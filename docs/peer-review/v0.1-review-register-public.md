# 3. R1 — Runtime Observation vs Execution Legitimacy

## Theme

**Runtime behavioral observation is distinct from runtime execution legitimacy.**

## Observation

Continuity should not be interpreted as simply preserving or comparing an authorization granted earlier.

The important distinction is:

```text
Authorization valid at t0
```

versus:

```text
Authorization still legitimate under governance state at t1
```

Runtime observation may tell the system what changed.

The governance control plane determines what that change means for execution.

## Architectural Interpretation

Continuity re-establishes alignment among:

- the bound authorization;
- the exact proposed consequence;
- current authority state;
- current evidence state;
- current policy;
- current approvals;
- current risk conditions;
- current execution context.

Proposed clarification:

> Continuity re-establishes the legitimacy of a bound authorization under the governance state that exists at the consequence boundary.

And:

> Runtime observation describes current state. Runtime governance determines what that state means for consequence.

## Impact

- Architecture: **No structural change**
- Continuity specification: **Clarification required**
- Invariants: **No new invariant**
- Implementation: **Continuity tests must include material current-state changes**

## Disposition

**Accepted for v0.1.1 clarification.**

# 4. R2 — Examination Boundary

## Theme

**A reference architecture should expose bounded claims that can be independently examined through evidence.**

## Observation

Independent examination becomes more meaningful when it can identify:

- architecture version;
- claims under examination;
- applicable invariants;
- system boundary;
- execution boundary;
- evidence required;
- test procedure;
- resulting finding.

The architecture should remain independently authored and should not need to be rewritten into an external examiner's terminology.

## Architectural Interpretation

This does not create another governance stage.

It introduces an **examination model around the architecture**:

```text
Architecture Version
        ↓
Claims Under Examination
        ↓
Applicable Invariants
        ↓
System Boundary
        ↓
Execution Boundary
        ↓
Evidence Required
        ↓
Test Procedure
        ↓
Finding
```

An initial bounded examination may be particularly useful around:

```text
Continuity
   ↓
Enforcement
   ↓
Route Closure
```

and invariants:

```text
C7
C8
C9
C10
C11
C12
```

## Impact

- Architecture: **No structural change**
- Specification: **Examination-boundary documentation may be added**
- Implementation: **Must preserve evidence capable of external inspection**
- Validation: **Creates a future independent-examination path**

**Accepted as an examination model.**

# 5. R3 — Contribution Boundary

## Theme

**Separate established architectural mechanisms from the specific contribution of this architecture.**

## Observation

Several mechanisms used by the architecture have established foundations in security, authorization, distributed systems, and execution governance, including:

- complete mediation;
- authorization binding;
- revocation;
- TOCTOU protection;
- fail-closed enforcement;
- provenance;
- execution-time validation.

The architecture should not imply that these mechanisms are individually novel.

## Architectural Interpretation

A suitable contribution boundary is:

> This architecture does not claim invention of complete mediation, TOCTOU protection, revocation, authorization binding, fail-closed enforcement, provenance, or related distributed-systems and security mechanisms.

Its contribution is the integration and decomposition of these obligations for consequence-bearing Agentic AI into:

```text
Admissibility
→ Binding
→ Continuity
→ Enforcement
→ Route Closure
→ Execution
→ Provenance
```

together with:

- C1–C15 invariants;
- explicit contracts;
- reference scenarios;
- executable proof obligations.

## Impact

- Architecture: **No structural change**
- Specification: **Contribution Boundary should be added**
- Positioning: **Avoid novelty overclaims**
- Research: **Prior work should be independently verified before citation**

## Disposition

**Accepted for v0.1.1 clarification.**

# 6. R4 — Authority vs Derived Permission

## Theme

**Execution authorization must not become the originating source of authority or standing.**

## Observation

An authorization artifact may be correctly bound, validated, fresh, and enforced while still leaving an ambiguity:

> Where did the legitimate authority represented by that artifact originate?

The system must distinguish between:

- principal or mandate;
- authority / standing;
- requesting actor;
- authorization issuer;
- execution authorization;
- authorized executor.

## Architectural Interpretation

The intended model is:

```text
Principal / Mandate
        ↓
Authority State
        ↓
Derived Execution Authorization
        ↓
Continuity Revalidation
        ↓
Execution
```

Normative distinctions:

```text
Standing ≠ Execution Authorization
Authority ≠ Execution Authorization
Execution Authorization ≠ Execution
```

An execution authorization is a **derived permission artifact**, not the origin of standing.

Its validity depends on an independently established and currently valid authority basis.

Implementation fields may include:

```text
authority_principal_id
authority_basis_id
delegation_id
authority_snapshot_id
authorization_issuer_id
subject_actor_id
authorized_executor_id
```

These identities may coincide in some implementations, but must not be silently collapsed.

## Impact

- Architecture: **Clarification of authority semantics**
- Execution Authorization contract: **Update required**
- Continuity contract: **Underlying authority basis must remain valid**
- Invariants: **No new invariant required**
- Implementation: **Authority source must be independently represented**

## Disposition

**Accepted for v0.1.1 clarification.**

# 7. R5 — External Runtime Evidence

## Theme

**External runtime measurement should remain evidence, not governance authority.**

## Observation

A clean interoperability point exists where an external system may provide runtime measurement evidence that is:

- signed;
- versioned;
- machine-readable;
- independently generated.

The external measurement provider should not itself decide:

```text
ALLOW
HOLD
ESCALATE
DENY
```

## Architectural Interpretation

The intended boundary is:

```text
External Runtime Measurement
        ↓
Signed / Versioned Evidence
        ↓
Governance Control Plane
        ↓
Evidence Interpretation
        ↓
Governance Decision
```

Core principle:

> Measurement evidence is descriptive. Governance interpretation is normative.

External measurements may affect:

- evidence state;
- capability state;
- continuity;
- risk;
- execution eligibility.

A minimal interoperability scenario is:

```text
AI Action
   ↓
Action Contract
   ↓
External Runtime Measurement
   ↓
Admissibility
   ↓
ALLOW
   ↓
Measurement State Changes
   ↓
Continuity Revalidation
   ↓
HOLD / ESCALATE
```

## Impact

- Architecture: **No structural change**
- Evidence semantics: **Clarification useful**
- Implementation: **External evidence adapters should be supported**
- Interoperability: **Concrete pilot pattern identified**

## Disposition

**Accepted as an interoperability requirement and future pilot pattern.**

The core runtime must remain independent of any specific external evidence provider.

# 8. R6 — Commit Semantics and Linearization

## Theme

**C6 and C8 require mechanically explicit commit semantics under concurrency and failure.**

## Observation

The conceptual execution sequence:

```text
Current-State Validation
        ↓
Authorization Consumption
        ↓
Protected Commit
        ↓
Execution Receipt
```

must eventually define a mechanically explicit **linearization point**, or provide equivalent transactional guarantees.

Relevant failure and concurrency cases include:

- concurrent replay;
- revocation racing commit;
- timeout after successful mutation;
- crash after mutation but before receipt;
- stale authority replicas;
- retry after ambiguous execution result;
- conflicting resource state at commit.

## Architectural Interpretation

A protected consequence cannot depend on a best-effort sequence such as:

```text
check authorization
then
check continuity
then
execute
then
mark authorization consumed
```

if another execution can race between those operations.

For single-use or tightly controlled protected actions, the implementation must coordinate:

```text
current-state validation
+
authorization consumption
+
protected mutation
+
durable execution evidence
```

through a defined linearization or transactional mechanism.

The architecture does not prescribe a specific technology.

Possible implementations include:

- transactional database operations;
- conditional writes;
- compare-and-swap;
- row-level locking;
- idempotency keys;
- transactional outbox patterns;
- durable execution journals;
- equivalent mechanisms.

## Required Adversarial Tests

Examples:

```text
test_concurrent_replay_only_one_commits
test_revocation_racing_commit
test_timeout_after_commit_does_not_duplicate_consequence
test_crash_after_mutation_preserves_recoverable_execution
test_stale_authority_replica_fails_safe
```

## Impact

- Architecture: **No new stage**
- C6/C8 semantics: **Implementation clarification required**
- Enforcement contract: **Commit semantics must become explicit**
- Provenance contract: **Receipt durability and recovery are relevant**
- Implementation: **High-priority proof obligation**

## Disposition

**Accepted as a core implementation requirement.**

# 10. R8 — Implementation Profiles and Route Closure

## Theme

**A vendor-neutral specification can be exercised through concrete implementation profiles without becoming defined by any one implementation.**

## Observation

Several control-plane responsibilities may be implemented through existing authorization, credential, verification, challenge, and transparency mechanisms.

However, a path verifier can establish that **the path presented to it** was governed.

That does not establish that no second path exists to the same protected consequence.

## Architectural Interpretation

A vendor-neutral architecture may support multiple implementation profiles:

```text
Normative Specification
        ↓
Implementation Profile
        ↓
Concrete Technology
        ↓
Executable Evidence
```

Core principle:

> One implementation of the specification is not the definition of the specification.

## Route Closure Implication

Route Closure remains a system-level property.

For every identified consequence-bearing path:

```text
AI Actor
   ↓
Possible Execution Route
   ↓
Protected State
```

there must be acceptable governance enforcement.

Example:

```text
PATH A
Governed Payment API
        ↓
Protected Account

PATH B
Legacy API
        ↓
Protected Account
```

If Path B can mutate protected state without equivalent governance:

```text
RouteClosure = FALSE
C11 = FAIL
C12 = FAIL
```

## Impact

- Architecture: **No structural change**
- Implementation model: **Implementation profiles should be supported**
- Route Closure: **Major executable proof obligation**
- Interoperability: **Future concrete profiles are appropriate**

## Disposition

**Accepted as an implementation and interoperability requirement.**

A native reference implementation should remain available so the architecture is not dependent on any one external implementation.

# 11. Consolidated Technical Findings

## 11.1 Current legitimacy, not historical permission

```text
Valid at t0
    ≠
Executable at t1
```

Continuity must determine whether authorization remains legitimate under the governance state existing immediately before consequence.

## 11.2 Authority must exist independently of authorization artifacts

```text
Mandate
   ↓
Authority
   ↓
Derived Permission
   ↓
Execution
```

The control plane must not silently relocate authority into the artifact used to enforce it.

## 11.3 External evidence does not own the governance decision

```text
Measurement
    ↓
Evidence
    ↓
Governance Interpretation
    ↓
Decision
```

This enables interoperability while keeping governance authority inside the control plane.

## 11.4 Commit semantics must survive concurrency and failure

The execution boundary must eventually define:

- when authorization becomes consumed;
- when revocation becomes effective;
- the linearization point or equivalent guarantee;
- retry semantics;
- duplicate-consequence prevention;
- partial-failure recovery;
- durable execution evidence.

## 11.5 Route Closure is a system property

```text
Governed Primary Route
        ≠
Governed System
```

Every identified semantically equivalent consequence-bearing path must either:

- cross acceptable enforcement;
- be equivalently governed;
- be explicitly and justifiably exempt;

or Route Closure must remain unresolved or fail.

## 11.6 Specification maturity must remain explicit

Current maturity:

```text
Architecture                COMPLETE
Normative Specification     COMPLETE
C1–C15 Invariants           SPECIFIED
Reference Scenario          SPECIFIED
Executable Runtime          NOT YET COMPLETE
Invariant Proof             NOT YET COMPLETE
Route Closure Proof         NOT YET COMPLETE
External Examination        NOT YET COMPLETE
```

Claims must not exceed demonstrated maturity.

# 12. Review Disposition

The v0.1 review does **not** currently require:

- a ninth architecture stage;
- additional C16+ invariants;
- renaming the architecture;
- replacing the control chain;
- merging the architecture with another framework;
- making an external protocol authoritative.

The review does justify a focused **v0.1.1 clarification release** covering:

1. contribution boundary;
2. authority / standing vs execution authorization;
3. continuity as current execution legitimacy;
4. runtime measurement vs governance interpretation;
5. commit / linearization semantics;
6. implementation maturity and Route Closure proof status;
7. examination-boundary semantics;
8. implementation-profile semantics.

---

# 13. Implementation Consequences

The executable reference implementation should be designed as an **adversarial consequence-control demonstrator**, not merely a happy-path application.

It should eventually exercise the architecture under conditions including:

- action mutation;
- wrong executor;
- expired authorization;
- replay;
- concurrent replay;
- authority revocation;
- stale authority state;
- policy changes;
- evidence changes;
- lost responses;
- execution retries;
- crash recovery;
- alternate execution routes;
- provenance tampering.

The detailed implementation architecture, technology choices, test plan, and external interoperability work should be documented separately from this peer-review register.

---

# 14. Closing Review Position

The v0.1 peer-review cycle materially strengthened the architecture without requiring structural redesign.

The principal transition is now:

```text
Architecture as Specification
          ↓
Architecture as Executable Claims
```

The next release should therefore be a limited clarification release rather than conceptual expansion.

After v0.1.1 is frozen, the primary proof obligation shifts to implementation:

> Can C1–C15 survive actual execution, concurrency, failure, stale state, replay, bypass attempts, and recovery?
