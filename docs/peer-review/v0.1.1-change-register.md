**Invariant status:** Frozen at C1–C15

## 1. Purpose

This register defines the exact changes to be made between v0.1 and v0.1.1.

The purpose of v0.1.1 is to:

- remove ambiguities identified during peer review;
- sharpen normative boundaries;
- make implementation proof obligations explicit;
- preserve the existing architecture and invariant structure.

v0.1.1 is **not** intended to introduce:

- a ninth architectural stage;
- new C16+ invariants;
- a replacement control chain;
- dependency on a specific external implementation;
- claims of implementation proof before executable evidence exists.

# 3. Planned Changes

## CHG-01 — Define the Contribution Boundary

**Source:** R3  
**Type:** Clarification  
**Risk:** Low

### Problem

The architecture uses mechanisms with established foundations in security, authorization, distributed systems, and execution governance.

The repository should not imply that these mechanisms are individually novel.

### Required Change

Add an explicit contribution boundary stating that the architecture does not claim invention of mechanisms such as:

- complete mediation;
- TOCTOU protection;
- revocation;
- authorization binding;
- fail-closed enforcement;
- provenance;
- execution-time validation.

Clarify that the contribution is their integration and decomposition for consequence-bearing Agentic AI through:

```text
Admissibility
→ Binding
→ Continuity
→ Enforcement
→ Route Closure
→ Execution
→ Provenance
```

together with:

- C1–C15;
- normative contracts;
- reference scenarios;
- executable proof obligations.

### Primary Targets

- `README.md`
- relevant architecture introduction material

### Acceptance Condition

The repository clearly distinguishes:

```text
Foundational mechanisms
        ≠
Specific contribution of this architecture
```

## CHG-02 — Separate Authority From Execution Authorization

**Source:** R4  
**Type:** Normative clarification  
**Risk:** Medium

### Problem

Execution Authorization may currently be interpreted as the source of authority rather than a permission artifact derived from independently established standing.

### Required Change

Make the following model explicit:

```text
Principal / Mandate
        ↓
Authority State
        ↓
Derived Execution Authorization
        ↓
Continuity Revalidation
        ↓
Execution
```

Add the normative distinctions:

```text
Standing ≠ Execution Authorization
Authority ≠ Execution Authorization
Execution Authorization ≠ Execution
```

State:

> An Execution Authorization is a derived permission artifact. It MUST NOT be treated as the originating source of authority or standing.

Its validity MUST depend on an independently established authority basis.

### Candidate Fields

```text
authority_principal_id
authority_basis_id
delegation_id
authority_snapshot_id
authorization_issuer_id
subject_actor_id
authorized_executor_id
```

### Primary Target

- `specifications/execution-authorization.md`

### Secondary Targets

- `docs/04-binding.md`
- bank-transfer scenario

### Acceptance Condition

A reader can clearly identify:

```text
who holds authority
who requested the action
who issued authorization
who may execute it
```

without assuming these are the same entity.

## CHG-03 — Revalidate the Underlying Authority Basis

**Source:** R4  
**Type:** Normative clarification  
**Risk:** Medium

### Problem

A cryptographically valid or unexpired authorization artifact may remain technically valid while the authority from which it was derived has changed or been revoked.

### Required Change

Continuity MUST validate both:

```text
Execution Authorization
        +
Underlying Authority Basis
```

at the execution boundary.

A valid token or authorization object alone MUST NOT establish current execution legitimacy.

### Primary Target

- `specifications/continuity-contract.md`

### Secondary Targets

- `docs/05-continuity.md`
- `specifications/execution-authorization.md`

### Acceptance Condition

Revocation or material change to underlying standing prevents inherited execution permission.

## CHG-04 — Define Continuity as Current Execution Legitimacy

**Source:** R1  
**Type:** Clarification  
**Risk:** Low

### Problem

Continuity may be interpreted as preserving authorization from `t0` rather than determining whether it remains legitimate at `t1`.

### Required Change

Add:

> Continuity re-establishes the legitimacy of a bound authorization under the governance state that exists at the consequence boundary.

Clarify:

```text
Valid at t0
    ≠
Executable at t1
```

Also distinguish:

> Runtime observation describes current state. Runtime governance determines what that state means for consequence.

### Primary Targets

- `docs/05-continuity.md`
- `specifications/continuity-contract.md`

### Acceptance Condition

Continuity is clearly a current-state governance decision, not a historical authorization comparison.

## CHG-05 — Separate Runtime Evidence From Governance Authority

**Source:** R5  
**Type:** Clarification  
**Risk:** Low

### Problem

External measurement or monitoring systems could be interpreted as having governance decision authority.

### Required Change

Make the boundary explicit:

```text
External Runtime Measurement
        ↓
Evidence
        ↓
Governance Interpretation
        ↓
Governance Decision
```

Add:

> Measurement evidence is descriptive. Governance interpretation is normative.

External systems MAY provide evidence affecting:

- capability;
- evidence state;
- risk;
- continuity;
- execution eligibility.

They MUST NOT automatically become the source of the governance decision.

### Primary Targets

- `docs/03-runtime-admissibility.md`
- `docs/05-continuity.md`

### Secondary Targets

- relevant specifications where evidence state is defined

### Acceptance Condition

External evidence providers can be replaced without changing governance decision ownership.

## CHG-06 — Define Commit Linearization Requirements

**Source:** R6  
**Type:** Implementation requirement  
**Risk:** High

### Problem

C6 and C8 can fail under concurrent or partially completed execution if validation, authorization consumption, mutation, and evidence generation are implemented as independent best-effort operations.

### Required Change

Define the required logical sequence:

```text
Current-State Validation
        ↓
Authorization Consumption
        ↓
Protected Commit
        ↓
Durable Execution Evidence
```

State that implementations MUST define:

- a linearization point;
- or an equivalent transactional mechanism preserving the relevant invariants.

The architecture must remain technology-neutral.

Possible mechanisms MAY include:

- transactions;
- conditional writes;
- compare-and-swap;
- locking;
- idempotency keys;
- durable journals;
- transactional outbox patterns;
- equivalent mechanisms.

### Primary Target

- `specifications/enforcement-contract.md`

### Secondary Targets

- `docs/06-enforcement.md`
- `specifications/continuity-contract.md`

### Acceptance Condition

The specification defines what must be atomic or equivalently protected without prescribing one infrastructure technology.

## CHG-07 — Make Concurrency and Failure Proof Obligations Explicit

**Source:** R6  
**Type:** Implementation requirement  
**Risk:** High

### Required Scenarios

The implementation requirements MUST include:

```text
concurrent replay
revocation racing commit
timeout after successful mutation
crash after mutation before receipt
stale authority replica
ambiguous retry
conflicting resource state
```

Canonical future tests should include:

```text
test_concurrent_replay_only_one_commits
test_revocation_racing_commit
test_timeout_after_commit_does_not_duplicate_consequence
test_crash_after_mutation_preserves_recoverable_execution
test_stale_authority_replica_fails_safe
```

### Primary Targets

- `specifications/enforcement-contract.md`
- `specifications/provenance-contract.md`

### Acceptance Condition

These cases are explicitly identified as implementation proof obligations rather than implied behavior.

## CHG-08 — Clarify Route Closure Maturity

**Source:** R8  
**Type:** Maturity clarification  
**Risk:** Medium

### Problem

C11 and C12 are currently specified, but route closure has not yet been demonstrated through executable bypass testing.

### Required Change

Explicitly state:

> Route Closure is currently a normative system property defined by C11 and C12. It becomes a demonstrated property only when executable evidence shows that identified alternate consequence-bearing paths cannot bypass equivalent governance.

Clarify:

```text
Governed Primary Route
        ≠
Governed System
```

### Primary Targets

- `docs/07-route-closure.md`
- `specifications/invariants.md`

### Secondary Target

- root `README.md`

### Acceptance Condition

The repository never implies that route closure has already been proven.

# 5. Change-Control Rules

For every file modification:

1. Preserve the existing eight-stage architecture.
2. Preserve C1–C15 numbering and meaning.
3. Prefer clarification over expansion.
4. Do not silently introduce new normative obligations.
5. Do not make implementation-specific technology normative.
6. Keep external systems optional and replaceable.
7. Preserve the distinction:

```text
Specification
≠
Implementation
≠
Evidence
≠
Independent Examination
```

8. Update cross-references only after the normative source text is settled.
9. Update the root README last.
10. Tag v0.1.1 only after a full cross-file consistency review.
